# lark-superbot：把飞书里的“事情”，变成可持续推进的 Task

> 一个以飞书消息为入口、以 Task 为中心、由 Agent 辅助调研和推进的工作协作工具探索。

## 一句话介绍

日常工作里，很多事情都从聊天开始：一个需求、一个问题、一句“帮忙看下”、一段补充说明。

但聊天适合沟通，不适合长期承载任务。消息会被新的讨论淹没，同一件事可能跨多个群、多个话题、多个 Agent Session，过几天再回头时，很容易遇到几个问题：

- 这件事现在推进到哪里了？
- 哪些信息是最新的？
- 当前结论依据什么？
- 下一步由谁处理？
- Agent 已经做过哪些调研？
- 换一个 Session 或换一个人之后，怎样继续？

`lark-superbot` 想做的事情很直接：

**把飞书里自然产生的工作事项，沉淀成可以持续跟踪、补充上下文，并由 Agent 辅助推进的 Task。**

---

# 1. 目前已经能做什么

当前版本已经跑通了一条个人工作场景下可使用的完整链路：

```text
业务群消息
    ↓
识别消息属于新事项 / 已有事项补充 / 无需处理
    ↓
形成或更新 Task
    ↓
自动进行一轮只读调研
    ↓
结果回写到对应 Task
    ↓
人决定是否继续 plan / exec
    ↓
后续结果继续沉淀在同一个 Task 上
```

目前它首先是一套 **单机、单使用者的任务入口和 Agent 调度原型**。

它不是一个“让 Agent 自动接管所有工作的系统”，当前设计仍然把关键动作放在人工控制之下。

---

# 2. 它能给日常工作带来哪些便利

## 2.1 不用再靠回翻聊天记录记住所有待办

很多工作事项并不会正式进入工单系统，而是自然产生在群聊里。

比如：

- “这个数据好像有问题，帮忙看一下”
- “这个需求后面还要补一个条件”
- “刚才那个方案再确认一下”
- “这个问题可能和昨天讨论的是同一件事”

这些信息如果只留在聊天里，后续通常要靠人自己记住、回翻、整理。

lark-superbot 会把接入的消息归纳为 Task，后续相关消息可以继续挂到同一件事上。

这样一来，聊天仍然是自然的沟通入口，但“事情本身”不再只存在于聊天时间线里。

---

## 2.2 同一件事的上下文可以持续累积

一个业务问题往往不会一次说清楚。

需求可能在上午提出，下午补充，第二天又出现新的背景信息。与此同时，Agent 可能已经做过一次调研，后来又需要重新计划或者执行。

如果这些信息分别存在于：

- 飞书群聊
- 私聊
- Agent Session
- 本地文件
- 代码仓库
- 临时笔记

后续再理解这件事时，就要重新拼一次上下文。

lark-superbot 会尽量把这些信息重新归到对应 Task 上，让 Task 成为这件事持续存在的“主线”。

---

## 2.3 新任务建立后，可以先让 Agent 自动做一轮只读调研

当前版本里，新 Task 建立以后，系统会自动拉起 Agent 做一轮只读调研。

这类调研适合完成一些前置工作，例如：

- 阅读相关代码和已有材料
- 理解当前实现
- 搜集上下文
- 初步分析问题
- 整理可能的影响范围
- 给出后续值得继续确认的问题

调研完成后，结果会回写到对应 Task。

这样人在真正开始处理之前，可以先拿到一份初步上下文，而不是每次都从零开始。

需要强调的是：

**自动调研不会直接进入修改或执行。**

调研结束后，任务会停在等待人工判断的状态。

---

## 2.4 可以从同一个 Task 继续让 Agent 研究、计划和执行

目前在台账话题中，可以通过明确指令继续推进：

```text
/research   补充调研
/plan       形成或更新计划
/exec       按计划执行
/stop       停止当前运行
```

这样做的好处是，后续 Agent 的工作不需要重新开一个完全独立的上下文。

它可以围绕同一个 Task 持续工作：

```text
Task
 ├─ 第一次调研
 ├─ 补充材料
 ├─ 第二次调研
 ├─ 计划
 ├─ 执行
 └─ 后续反馈
```

从使用体验上看，它更接近：

**“让 Agent 围绕一件事持续工作”**

而不是：

**“每次重新找一个聊天窗口问 Agent 一个问题”。**

---

## 2.5 业务群和 Agent 工作过程分开，减少信息噪音

当前系统把两个工作面拆开：

### 业务群

业务群负责自然产生事项。

成员只需要正常讨论，在必要时 `@Bot` 或相关用户，让消息进入系统。

业务群里只返回简短回执，不会把长篇 Agent 输出、运行日志和执行过程全部倒回原群。

### 台账群

每个 Task 会有自己的话题。

Agent 调研结果、运行状态、后续指令都集中在这里。

这样的好处是：

**业务讨论和 Agent 的工作过程不会混在一起。**

业务群继续保持可读，真正需要关注 Task 细节的人，再进入对应话题查看。

# 3. 一个典型使用过程

假设群里出现这样一条消息：

> 最近某个数据结果不太对，怀疑和新上线的逻辑有关，能不能帮忙确认一下？

系统收到消息后，大致会经历下面几个步骤。

### 1. 判断这是不是一件需要处理的事情

Dispatcher 会结合消息上下文和当前已有 Task，判断它属于：

- 新建 Task
- 已有 Task 的 followup
- 与任务无关，无需处理

### 2. 创建 Task

如果识别为新事项，系统会为它建立独立 Task，并记录：

- 标题
- 简要说明
- 当前状态
- 来源群和话题
- 所属项目
- 工作区位置
- 台账位置

### 3. 自动进行只读调研

Agent 会先做一轮不产生业务副作用的调研，例如查看代码、现有资料或上下文。

调研完成后，把摘要写回对应 Task。

### 4. 人决定下一步

如果调研结果已经足够，人可以直接结束。

如果还需要进一步工作，可以继续：

```text
/research
/plan
/exec
```

系统不会因为一次消息分类或一次 Agent 判断，就自动获得修改业务系统的权限。

# 4. 目前几个核心对象

lark-superbot 现在的一个核心设计是：

**业务上的“一件事”，不应该等同于一次 Agent Session。**

一件真实的工作事项可能经历：

```text
Task
├─ Session A：理解需求
├─ Session B：补充调研
├─ Session C：讨论方案
├─ Run 1：查询和诊断
├─ Run 2：修改和测试
└─ Run 3：根据反馈返工
```

Session 会结束，Run 会成功或失败，但业务上的“这件事”仍然存在。

因此目前会把几个概念区分开。

## Task

Task 表达业务上的“一件事”。

它负责保存这件事的稳定身份和当前状态。

例如：

- 这件事是什么
- 当前推进到哪里
- 来源在哪里
- 下一步是什么
- 关联了哪些材料和运行结果

## Event

Event 表达围绕 Task 已经发生的事实。

例如：

- Task 被创建
- 收到新的补充信息
- 状态发生变化
- Agent 开始一次运行
- 一次运行结束
- 人作出一个决定

Task 更像“现在是什么状态”，Event 更像“它为什么变成现在这样”。

## Clue

当前版本中的 Clue 用来把相关资源挂回 Task，例如：

- 飞书消息
- 飞书话题
- Cursor Session
- 代码仓库

目前它首先是一层资源索引，还不是完整的证据模型。

## Run

Run 表达一次具体的 Agent 调研或执行。

一次 Task 可以经历多次 Run。

所以：

**Run 完成，不代表 Task 完成。**

---

# 5. 当前已经具备的一些工程能力

除了任务主链路，目前原型已经具备一些基础运行能力，包括：

- 消息持续接入
- 消息队列
- Agent 队列
- 基础失败重试
- 租约和心跳
- 运行锁
- 进程标识
- 同一个 Task 同时只允许一个 Agent Run
- 调研结果回写 Task
- 人工停止当前运行

这些能力的目标不是把系统做得“很重”，而是保证它作为一个长期运行的工具时，不至于因为重复消费、重复拉起或单次失败，让 Task 状态失控。

# 6. 哪些场景比较适合现在拿来用

当前版本比较适合下面几类个人工作场景。

## 场景一：群里经常会冒出零散待办

如果一个人的工作里，经常会从不同群里收到很多临时事项，lark-superbot 可以先承担“收件和归档”这一层工作。

减少：

- 反复回翻聊天记录
- 手工整理待办
- 忘记后续补充
- 同一问题重复建立上下文

---

## 场景二：一个问题经常要经过多轮 Agent 调研

有些问题不会一次问完。

可能先让 Agent 看代码，再补充日志，再让它形成方案，然后才执行。

这类情况下，把工作围绕 Task 组织，比单独维护多个 Session 更容易追踪。

---

## 场景三：需要把“Agent 能做什么”和“什么时候必须由人决定”分开

当前链路默认会在关键位置保留人工闸门。

例如：

- 自动做只读调研
- 人决定是否继续计划
- 人决定是否执行
- 可以随时停止运行

这比较适合那些希望使用 Agent 提高效率，但又不希望它在没有明确授权的情况下自动修改业务环境的场景。

---

# 7. 当前边界

目前已经跑通的是：

- 飞书消息持续进入系统
- LLM 在个人工作场景中做基础语义归纳
- 消息可以形成新 Task 或已有 Task 的补充
- 创建 Task 后自动完成一轮只读调研
- 人可以从台账继续发起调研、计划、执行和停止
- 运行结果持续回到同一个 Task

当前还没有完成或充分验证的是：

- 多用户身份和 Task 级权限控制
- 多人、多群、多事项下的稳定归类
- 完整的跨 Session / 跨人协作
- 面向其他 Agent 的标准 Task 工具面
- 逐动作授权和服务端权限校验
- 完整的决策请求和恢复点
- 企业级管理分析和知识沉淀

所以现阶段更适合把它理解为：

**一个已经可以使用的个人 Task + Agent 协作原型。**

后面的很多能力，目前仍然属于设计和探索方向。

---

# 8. 后续可能进一步展开的三个方向

下面这三层不是当前已经实现的能力，而是建立在现有 Task / Event 模型之上的进一步设想。

## 第一层：优化协作方式

第一层最直接。

希望解决的是：

### 事项容易遗漏

把聊天中产生的事项沉淀为稳定 Task，而不是依赖人定期回看消息。

### 同一个群里多件事容易串上下文

让不同业务事项拥有独立上下文，避免多个问题混在同一段聊天时间线里。

### 同一件事需要反复同步背景

如果 Task 能稳定记录目标、状态、材料和结论，后来参与的人就不需要重新听一遍完整口述。

这一层关注的仍然是：

**怎样让人和人之间围绕同一件事协作得更顺。**

---

## 第二层：优化人与 Agent 的工作方式

如果 Task 真能成为稳定的业务对象，下一步才有可能让 Agent 不只是“回答问题”，而是围绕 Task 持续推进。

理想状态下：

```text
Task
    ↓
Agent 在授权范围内继续处理
    ↓
遇到需要人判断的问题
    ↓
整理成一个清晰的决策请求
    ↓
人只处理关键判断
    ↓
Agent 从原位置继续
```

这里真正希望改变的，不只是“让 Agent 多做一点”。

而是把人的工作逐渐从：

```text
理解问题
→ 搜材料
→ 调研
→ 设计方案
→ 判断风险
→ 执行
→ 跟进
```

变成更多聚焦在：

```text
定义目标
→ 关键判断
→ 授权
→ 验收
```

当然，这一层成立的前提非常多：

- 权限边界必须可靠
- Agent 要能恢复上下文
- 每一步动作需要可追踪
- 写操作不能仅依赖 Prompt 约束
- 执行结果需要独立校验

因此目前它仍然是方向，而不是现成功能。

---

## 第三层：形成管理和知识价值

只有当前两层真正稳定运行后，Task / Event 才可能进一步产生团队和组织层面的价值。

例如：

### 看见真正的工作卡点

可以观察：

- 哪些 Task 长期等待决策
- 哪些任务经常因为权限或资源卡住
- 哪些步骤 Agent 已经可以稳定完成
- 哪些类型工作仍需要大量人工介入

### 沉淀可复用知识

如果长期运行中积累了真实的：

- Task
- Event
- Decision
- Run
- 结果

就可能逐渐识别：

- 重复问题
- 可复用方法
- 稳定操作流程
- 可以沉淀成 Skill 的工作模式

这一层的前提仍然是：

**底层记录必须真实、稳定、可追溯。**

如果 Task 本身都记不准，再往上做管理分析或者知识提炼，只会把误差放大。

---

# 9. 我目前最想验证的问题

这个项目现阶段真正值得继续观察的，不是“还能加多少功能”，而是几个更基础的问题：

1. **Task 能不能稳定成为业务上的“一件事”**
2. **消息和上下文能不能可靠地归到正确 Task**
3. **围绕 Task 工作，是否真的比围绕 Session 工作更自然**
4. **Agent 的调研和后续工作，能否持续复用已有上下文**
5. **人工闸门是否能在效率和安全之间找到合适平衡**
6. **这套方式是否真的能减少遗漏、重复解释和上下文恢复成本**

如果这些问题成立，后面的多用户协作、自动推进和知识沉淀才值得继续讨论。

# 结语

lark-superbot 当前还不是一个完整的协作平台。

它更像是在回答一个具体问题：

> **当越来越多工作开始由人和 Agent 一起完成以后，业务上的“一件事”应该由什么来持续承载？**

目前的答案是：尝试让 Task 成为这个稳定对象。

飞书消息负责产生事项，Session 负责交互，Run 负责执行，Event 负责记录发生过什么，而 Task 负责让“这件事”在时间、Session 和 Agent 之间持续存在。

现在这套东西已经可以在个人工作流里跑起来。

至于它最终只是一个更好用的个人任务入口，还是能够进一步延伸成团队协作和 Agent 工作基础设施，还需要继续用真实工作场景来验证。
