# lark-superbot：把飞书里的“事情”，变成可持续推进的 Task

日常工作里，很多事情都从聊天开始。需求在上午提出，下午有人补条件，第二天又有人纠正上个月的数据。同一件事可能跨多个群、多个话题、多个 Agent Session，过几天再回头时，很容易遇到几个问题。

- 这件事现在推进到哪里了？
- 哪些信息是最新的？
- 当前结论依据什么？
- 下一步由谁处理？
- 换一个 Session 或换一个人之后，怎样继续？

这份团队分享记录飞书原型验证过的能力，并用一个月度交付解释下一版的协作方式。完整的角色职责见[方向与设计](blueprint.md)，实施与验收顺序见[项目路线图](20261119-task-coordination-roadmap.md)。

## 飞书原型已经做到了什么

当前仓库中的 Gateway 接入已绑定业务群，业务 bot 收到提及它或所代理用户的消息后，将事件放入持久队列。内网 daemon 领取消息，dispatcher 查看飞书上下文、任务契约短稿和已有任务，在创建、跟进和略过之间做一次选择。默认台账 bot 在台账群同步任务及后续记录。代码中的业务群自动短文本回执已关闭，用户仍可明确使用消息工具回复原消息。[分发回执实现](../app/services/dispatcher/ack.py)

原型中的执行流程也解释了下一版为什么要调整边界。配置开启自动调研时，新建任务可以进入 agent 队列，agent worker 再请求 Gateway 运行 Cursor CLI。台账话题中的 `/research`、`/plan`、`/exec`、`/stop` 操作这套服务端运行流程，因此项目文件、Cursor 环境和进程锁与 Gateway 所在机器相关。计划中的 VPS 承接飞书消息并保存任务和运行记录，内网 daemon 负责启动角色 agent。需要维护现有部署时，可参阅[当前运行说明](../README.md)。

队列、租约、心跳、幂等跟进和台账同步补偿都已有实现。11 月上线的五个 MCP 工具支持按群查任务、读契约与近期事件、看入站上下文、追加备注和回复消息。该版本的一次分发只记录一个目标任务，任务存储仍将 `done` 和 `cancelled` 作为终态。下文的消息多投、稳定后重开和人工接管属于目标设计。[MCP 上线记录](20261117-mcp-rollout-and-roadmap.md)

## 交接时各自要读什么

一个业务问题往往不会一次说清楚。第一次会话里的计划可能被后来的一条消息纠正。接手人既要找到最新契约，也要能回看当时为什么改变方向。例如同一件事可能留下以下记录。

```text
Task
├─ Session A：理解需求
├─ Session B：补充调研
├─ Session C：讨论方案
├─ Run 1：查询和诊断
├─ Run 2：修改和测试
└─ Run 3：根据反馈返工
```

Session 会结束，Run 会成功或失败，但业务上的“这件事”仍然存在。这里的分支是关联记录；下一版界面中的任务树则专门表达交付的父子关系。

| 对象 | 回答的问题 | 一个具体例子 |
|---|---|---|
| Task 与契约 | 这次承诺解决什么、边界在哪里、如何验收、何时停止？ | 处理 9 月验收口径，交付经确认的退款归类；10 月收数是另一项交付 |
| Event | 已经发生了什么？ | 某人在原话题中提供口径依据、owner 修订验收条件、人接管了任务 |
| Clue | 去哪里查看相关材料？ | 消息、话题、代码仓库或与任务相关的会话索引 |
| Run | 哪个进程在什么条件下做了哪一轮工作？ | worker 向业务方发出澄清后退出，等回信再开始下一轮 |

任务叙事让新接手者读到当前判断、尚缺的证据和下一步。契约规定交付本身。A 把问题转给 B，owner 更新叙事和等待对象；B 如果给出与旧口径冲突的新依据，owner 再判断是否需要改契约。每次修改留下原因与来源，便于后人看清谁在什么时候改变了要求。

## 目标工作流：一条消息跨了两期

> “10 月源表到了，另外 9 月验收时要把退款剔除。”

1. **飞书收件与路由。** VPS 保存一次入站。内网 router 使用项目期次、流程步骤、直接引用和相关任务摘要选择目标，把前半句挂到 10 月收数、后半句挂到 9 月验收。只有后一项承诺可能要变时，就只给 9 月 task_owner 一项待办。需要处理但找不到归属的证据交给项目根。
2. **维护任务。** 本地 daemon 领取待办，按任务号和角色 skill 启动 task_owner。它核对旧契约，写明更改范围或尚待确认的问题，更新叙事与检索标签。独立可验收、需要单独等待或单独交付的事项可以建为子任务。项目根及其子任务构成责任树，消息与任务的多对多关联另外保存。
3. **处理与交付。** 第一版由人在本地 Codex 或 Cursor 会话里挑选任务，从工具读取契约和必要来源，按 worker 身份提交交付物、依据或阻塞。worker 有权提请复核范围，契约变动由 owner 处理。一个 run 结束后，该任务仍可能等待业务方答复。
4. **稳定与重开。** 验收通过的任务可以进入稳定态。日后有人更正 9 月口径时，这项历史任务仍能被检索。owner 依据原契约区分修订原交付或另开承诺，并保留上次验收记录。试点先由人验收，重复且可判定的交付再引入项目配置的 supervisor。

## 当 agent 需要和人核实

以“确认退款是否包含在本期交付中”为例，澄清子任务写明需要确定的要点与可接受的结论。worker 问 A，A 转介 B，就把转介依据、B 和等待条件记在同一任务里继续跟进。B 的原话能证明这个问题不适用，也是一项有依据的结果。无回复则保留未决状态，按约定提醒或移交。

目标系统需要把外发的提问与任务关联，让 B 在原话题里直接回答也能唤醒正确的工作。现行收件按已绑定群中的 `@bot` / `@用户` 过滤，这个普通回复场景要在试点单独验证。

人也能主动改变方向。假如你在等待 B 时接管任务，B 后到的消息应能归档，旧运行不能继续代你发问或覆盖你的决定。你可以改目标、自己处理或明确恢复自动执行。这个场景和“一次请求重试不产生第二次外发”一起作为自动 worker 的试点验收。

## 哪些日常工作值得拿来试

原型最常见的入口是群里的一句“这个数据好像有问题，帮忙看一下”。几天后换人或换会话，接手者应当能直接找到当初报错的消息、已经排除的原因、还有谁在等反馈。业务群保留提问与答复，台账和任务详情保留处理经过。对照以往靠回翻聊天拼出背景的做法，可以实际观察有没有减少漏项、重复解释和返工。

团队以后也可以从长期等待的任务发现共同卡点，从多次人工验收中提炼可复用的项目 skill。这些判断依赖真实的记录。一次运行结束后先核对业务结果和证据，再把这一单计入完成或返工。

## 团队分享时可以怎样演示

- 先演示当前原型可以复现的操作：从任务详情找到来源消息，查看台账跟进与会话线索，换一个会话继续查同一任务。具体工具名和调用示例见[现行使用文档](../README.md)。
- 再用脱敏的相邻两期消息演示目标流程。逐条比较人工标注与 router 的候选、命中和唤醒，标出究竟是检索漏掉上期任务，还是候选在场但月份选错。用干净会话检验 owner 写下的交付、边界和停止条件能否被 worker 准确复述。
- 单项目试点先看根节点积压、错挂、等待对象和人工纠正。只读任务树在这个阶段可以帮助解释这些记录。是否扩大自动执行、升级 router 后端或引入自动验收，根据真实交付、返工和接管回放来定。[实施与评测路线图](20261119-task-coordination-roadmap.md)
