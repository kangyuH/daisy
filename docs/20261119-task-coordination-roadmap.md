# 人与 agent 协作的任务记事本路线图

2026-11-19 · 设计提案。第一个可用版本的目标是让一个项目真正用起来：router 只挂消息，本地 daemon 自动拉起 task_owner，人通过 Codex / Cursor 挑选任务、充当 worker。下面的验收条件用于决定何时扩大自动化范围。

[产品蓝图](blueprint.md)约定各角色的职责、任务树、契约与人工接管语义。本文是对应的实施与验收计划。[2026-11-17 MCP 上线记录](20261117-mcp-rollout-and-roadmap.md)记载已有的五个 MCP 工具；[契约设计说明](task-contract-design.md)记录当前版本的初稿与保存方式。

## 部署与角色

VPS 保存任务树、版本化契约、叙事、来源消息、任务关联、角色待办和运行记录，飞书 CLI 在此收发消息。内网 daemon 经受控 REST 领取、续租和确认待办，根据角色、任务或入站编号、触发原因和 skill 版本启动本地 agent。项目的期次、标准步骤、业务用语和判断规则由内网配置提供；VPS 保存相应项目和任务的稳定标识。人工可以随时通过客户端查看、接管、纠正和恢复。

| 角色 | 可以做的决定 | 服务端可验证的边界 |
|---|---|---|
| router | 一条入站的不同原句归到哪些已有任务，哪些交项目根处理，哪些与任务无关 | 挂原文、理由和来源。不能建任务、改契约或启动业务执行 |
| task_owner | 维护目标、边界、验收与停止条件，以及叙事、标签、子任务和下一步委托 | 基于读到的版本写入。角色工具和运行环境都限制到维护任务所需范围 |
| worker | 依据契约完成委托，记录证据、交付、阻塞或对契约的异议 | 可以提出变更请求，契约修改交回 owner。对外发送记录操作归属和幂等键 |
| 人 / 后续 supervisor | 人接管并裁决方向；可按项目将部分代码 review 或交付 QA 委托给 supervisor | 人接管后旧运行不能再提交受控写入或外发。验收意见引用本次契约版本与交付物 |

## 六个阶段

| 阶段 | 实施与交付 | 进入下一阶段的依据 |
|---|---|---|
| 0 · 一项目、两期、离线回放 | 选一个真实月度项目，手画项目根、两个月份及必要步骤。用几十条脱敏入站做第一版 eval，人工标出理想归属和处理动作。现有 LangChain dispatcher 提供单目标参照 | 能用样本区分跨期、同消息两件事、旧任务更正和归属不清。得到可重复运行的基线和第一批错误案例 |
| 1 · VPS 新账本，可人工跑通 | 新库建立项目根、单父节点且无环的树、消息与任务的多对多关联，契约及修订在同一事务保存。建立未归属待办、来源和运行记录。提供最小角色 MCP 工具。旧 researcher、agent 队列和台账执行命令退出新部署。先由人充当 owner 和 worker | 新会话能找任务、读原文、改契约、建子任务、交付结果和回飞书。同一消息重放不重复挂证据；两个人改同版契约能看到冲突；休眠任务仍可查到 |
| 2 · 单项目实装三角色，自动 owner、手动 worker | 先给一个项目根安排好 owner 和人工兜底。router 在副本上运行、比对后再切 follow-only。需要维护的路由结果与 owner 待办一起可靠落库。daemon 按任务号用一个通用 CLI + 本地版本化 skill 启动 owner；owner 整理后退出。worker 由人挑任务开会话 | 跨期消息分别落到正确任务；新事项在根被接住并由 owner 创建或重新归属；重复入站、owner 重启不会重复建子任务或循环唤醒。人工能纠错、接管、恢复。到此即可作为第一版日常使用 |
| 3 · 看清谁在做什么，再扩客户端 | 阶段 2 试点即可开工只读 WebUI，呈现项目折叠树、等待对象、证据来源、契约变更、根节点积压和上一次唤醒原因。读模型稳定后发 task resources。用同一批回放比较 LangChain router 与通用 agent + skill | 人能在界面解释错投，找到等待或失联的任务；客户端可按同一任务 URI 读到与工具一致的版本和权限。新 router 在质量、延迟和成本上达标后单项目切换，可切回旧运行后端 |
| 4 · 一类 worker 自动运行 | 从重复、边界明确、容易验收的任务类型开始，例如按固定规则检查交付清单。先生成草稿供人审核，再按类型开放自动交付。需要外部答复时保存提问与等待条件，退出进程，回复或约定到期再唤醒。补上日常需要的 WebUI 接管、恢复和复核操作 | 独立新会话只凭任务即可交付；重复领取不重复发送；B 不 @bot 的话题回复能关联；接管期间迟到的回复只归档；旧运行失效；恢复后只执行一次。上线后人工改判和返工在预定范围内 |
| 5 · 按证据扩展 | 将人工反复采用的验收标准写成项目 supervisor skill，先旁路出意见；用好坏交付对照校准后再委托部分验收。第二个 runner 用同一任务验证启动、工具权限、重试、取消和结果回报。多机分发有实际需求后发 Skills over MCP。检索随规模扩展 | 能以项目或任务类型单独关闭自动化；能追溯每个结果的契约、模型、skill 和证据版本；扩项目、换 runner 后仍通过同一组关键回归 |

阶段 3 的界面、resources、router 后端替换可独立发布。自动 worker 的前置条件是能观察、接管和验收；这些能力可先由 MCP / CLI 提供。打通一个 CLI 后即可做第二个后端的小型兼容性试验。

## owner 何时拆任务

先问能不能给子任务写出独立的交付结果和停止条件。再看它是否需要单独委托、等待、并行推进、暂停或重开。两方面都成立，拆分就有收益。五个标准步骤先用作项目知识。某一步需要独立接收消息、验收或推进时，owner 才把它实例化为该期的子任务；其余步骤保留在检查清单。

例如“等业务方明确本月退款如何归口”可以成为澄清子任务。A 转介 B 后继续同一个子任务；B 说明这一问题不适用并给出依据，也可以满足停止条件。一次消息涉及两个交付时分别挂证据即可。父 owner 负责整体验收，子任务的完成只是其中一项证据。

任务的业务进展、当前控制权和某一次运行的状态分别记录。稳定任务可因新证据再次进入 owner 待办。人工接管期间照常收件，是否恢复自动处理由人决定。

## eval 从第一条消息开始搭

### 第 0 阶段的最小工具

版本化保存脱敏样例、预期结果和逐条判定报告。一条样例要能还原消息到达时的任务树、契约版本、群与项目配置、可见的回复链，以及角色能调用的工具。回放用临时账本和模拟飞书出站，固定事件顺序，可注入重试、断线和接管。保存实际候选、最终挂载、是否唤醒、工具调用、结果、耗时和模型用量。先让一条命令可以比较两版实现。

用一个真实项目相邻两期的约 20–40 条消息起步。这个量适合发现结构性错误，不能说明总体准确率。人工标注允许多个正确目标，区分“相关但只需留证”“需要唤醒 owner”“根待判断”“无关”，保留理由和可接受的替代处理。开发集用于调 skill；留出一批新话题或后一期事件，只在版本比较时运行，同一 thread 不横跨两组。任何运行时输入只可使用当时已知信息。

建议首批包含这样一例：“10 月源表到了，另外 9 月验收口径要排除退款”。期望挂上两份证据；在样例约定 10 月仅待收件、9 月契约可能需变更时，只触发 9 月 owner 复核。将同一入站再投一次，新增关联、待办和外发均应为零。如果候选列表里没有 9 月任务，修检索；有候选却选错月份，修项目上下文或 router。

### 各角色用不同的判据

| 对象 | 观察或断言 | 用来决定什么 |
|---|---|---|
| 检索与 router | 正确任务是否进入前 K 个候选；最终目标集合的查全率、查准率；单独统计跨期误投、第二目标漏投、根待判断、误唤醒，以及延迟、调用成本 | 先补期次、回复链、叙事或标签。用回放验证全文或语义检索是否值得引入。比较两种 router 时用相同定义的候选与工具；另测包含检索的全链路 |
| owner | 让人对照原消息判断契约差异是否有依据、是否扩大承诺、能否验收；拆分或保持单任务的理由；叙事有无遗漏关键事实。另开新 worker 读契约，说出交付、边界和停止点 | 先准许低风险自动维护，人工抽查分歧大的变更。按项目记录改判及返工原因，并补进回归集 |
| worker 与 supervisor | 比较结果与契约中的验收项，记录交付物、外部效果、人工返工。用已知有缺陷与合格的结果测 supervisor 漏放和错拦。遇到确有争议的业务判断保留人工裁决 | 按任务类型决定自动化范围。验收优先使用可执行检查和来源证据，开放判断由人工标注；模型评分器可辅助筛选案例 |
| 服务与 daemon | 重放重复消息、过期租约、旧契约写入、owner 维护触发自身、提问后宕机、人工接管后旧 run 写回、B 无 @ 回复。核对最终账本与外发次数 | 重复外发、越权写入和接管失效等确定性测试出现一次即修复并重跑，再开对应自动化 |

### 上线后继续评

先旁路生成建议，逐条比较人工或现行决定；再选一个项目或一类任务试运行。监控根待办寿命、人工重新归属、改契约、重开、重复外发、等待超时和每条有效分发的成本。每轮发布既复跑冻结集，也抽查近期真实消息，包括无人纠正的样本。模型、项目配置、skill 或协议变动时，以相同输入比较；对有随机性的关键案例重复运行，保留波动。业务阈值与人工可接受的返工量、漏投代价和响应时间一同商定。

## MCP、runner 和界面的交付边界

- **MCP tools 在阶段 1 就补。** 提供搜任务、读详情与来源、挂消息、按版本保存契约、创建子任务、记录进展或等待、交付结果、回消息，以及人工接管与恢复。按调用身份授予子集，按动作验权限、任务版本和重试键。daemon 的 claim / heartbeat / ack 继续走受控 REST。
- **Task resources 在读模型稳定时发。** 搜索或项目树返回小批候选和稳定 URI，例如 `task://project-a/42/contract`。通过资源模板按需读摘要、契约和证据；保留读工具兼容不同宿主。写入通过带版本条件的工具，WebUI 与 MCP 使用相同领域逻辑。[MCP Resources 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)
- **Owner 首先使用通用 agent + skill。** daemon 初版只需把任务、触发原因、可用工具、skill 版本交给一个可取消的 CLI，并取得可核对的结果。LangChain router 先改成相同的 follow-only 语义作基线。再对照通用实现的漏投、误投、冷启动、P95 延迟、重试与成本，达标即可按项目替换。框架替换不应阻塞 owner 上线。
- **Skills over MCP 用于跨机器分发。** 先把旧 superbot skill 的通用工作约定与 router、owner、worker 的版本化本地 skill 拆开。确有多项目、多 runner 升级需求时，再发布已验证的版本并提供回退。目标宿主逐一测试发现、激活、引用文件与版本校验。扩展定义 `skills/list`、`skills/get`，文件通过 `resources/read` 读取；宿主负责激活。即使远程分发，运行记录也应固定所用版本。[MCP Skills 扩展](https://skills.extensions.modelcontextprotocol.io/)

## VPS 切换与第一批工程任务

在试验回放的同时准备 VPS 新库和飞书测试群。旧账本归档；区分新旧任务编号；恢复飞书用户、默认台账 bot 和业务 bot 配置，重建群与项目映射。用持久盘上的单实例数据库做备份恢复演练。MCP 对客户端提供 HTTPS，daemon 主动连受控 REST。按 bot 切换长连接接收端；如一个 bot 服务多个群，在同一接收端按项目分配新旧处理流程。旁路试验消费记录副本，对外发送只有一个执行方。回退时先暂停新调度，核对切换窗口的入站及已经外发的消息，再恢复选定的处理流程。

建议先拆出以下三项可独立验收的工程工作：

1. 建两期样例、人工标注和一个可重放的路由 eval，交付现有基线与失败案例。
2. 在新账本跑通“同消息关联两期、未归属挂项目根、人工 owner 建子任务、手动 worker 交付”，并验证去重和接管。
3. 将同一条路径中的 owner 换成 daemon 拉起的本地 agent，记录运行证据，在试点项目上保留人工纠正入口。
