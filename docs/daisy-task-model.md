# 任务身份与边界

这份说明供 router 判断消息归属、task_owner 维护契约、worker 判断是否接手。文中的树、角色和唤醒规则是新账本的设计目标。当前服务的 `0.1` 契约读写方式见[契约设计](task-contract-design.md)。[产品方向](blueprint.md) · [实施路线与评测](20261119-task-coordination-roadmap.md)

## 1. 核心定义

**可交付的任务代表一份有边界、可验收的结果承诺。** 每个项目另有一个根节点，承接新事项和待判断的消息。根节点的 owner 负责分诊。

拿到 Task 后，Agent 应能回答：

1. 需要让什么事情发生变化？
2. 对哪些业务对象、时间、环境和人群负责？哪些不在范围内？
3. 什么结果算完成？哪些判断需要人来做？
4. 最终交付什么、交给谁、通过哪里反馈？
5. 哪些关键信息仍未知，澄清前能做什么、不能承诺什么？

来源可以有多个，但一个 Task 应当对应**一份连贯、可以判断是否完成的结果承诺**。标题、群聊、会话和 Agent 运行都不能单独定义 Task 的身份。

## 2. 精简契约与按需补充的背景

日常交接先写四项：交付目标、对象与期次及边界、验收所需证据、停止或交回的条件。以下维度是补充背景时的参考。例如涉及业务方拍板时，owner 再写清谁能验收。

| 维度 | 要回答的问题 | 建议记录的内容 |
| --- | --- | --- |
| 创建缘由（Origin） | 为什么产生这项任务？ | 触发来源、最初的业务问题、与父任务的关系；来源可以是飞书消息、工单、其他 Task 等，也可以逐步汇集多个线索 |
| 目标（Objective） | 希望得到什么业务结果？ | 预期变化或结论、结果作用的业务对象 |
| 范围（Scope） | 这份承诺管到哪里？ | 纳入项、排除项、适用时间、环境、人群、必要约束 |
| 验收（Acceptance） | 怎样证明结果已达成？ | 可检查的结果条件、交付要求、接受方式和决定权 |
| 反馈约定（Feedback） | 结果交给谁、交到哪里？ | 接收方、反馈位置、反馈内容与形式 |
| 相关方（Parties） | 谁能提供信息、支持或决定？ | 需求方、验收方、结果接收方、外部支持方及各自职责 |

沟通、证据和运行分别留痕。owner 用简短叙事概括目前已知、尚缺什么和下一步，并维护检索标签。

### 目标与验收的区别

**目标**描述业务上希望成立的事实；**验收**描述如何确认它成立。验收可以再拆为：

1. **结果条件**：必须成立的事实或达到的标准。
2. **交付要求**：必须留下什么可检查的产物或依据。
3. **接受方式**：Agent 可以依条件自行判定，还是必须由指定的人确认。

例如，业务方说“昨天的渠道收入数据不对，帮忙看一下”，若约定本次只负责调查：

| 项目 | 可能的定义 |
| --- | --- |
| 目标 | 查明指定日期渠道收入差异的原因，为是否修复提供依据 |
| 范围 | 指定报表、日期、渠道及相应计算链路；不负责修复数据或重跑生产任务 |
| 交付物 | 原因分析和处理建议 |
| 验收条件 | 说明差异口径与数值；定位原因并给出依据；说明影响范围；提出处理建议或明确尚不能判断的部分 |

“写出报告”只证明交付物存在；“问题已查明”如果没有证据标准，也不足以让 Agent 判断完成。探索性任务还应约定**调查到什么程度可以结束**：例如完成指定核查后仍未定位时，交付已排除项、剩余假设和下一步所需材料，并由需求方决定是否接受。临时缺材料通常意味着受阻，不能由 Agent 自行把目标降格为已完成。

### 来源、反馈与决定权

应分别表达：

- **来源**：承诺为何产生、最初依据是什么。
- **结果接收方**：谁需要取得或使用结果。
- **反馈位置**：结果发布到哪个飞书 thread、工单或其他位置。
- **验收方**：谁有权认定结果符合要求。

飞书 thread 是位置，不是一个人或一项决定权。可以默认反馈到触发任务的 thread，但这个默认值应允许调整，也不参与任务身份判定。子任务常向父任务交付结果，子任务完成也不自动意味着父任务完成。

### 相关方的职责

| 角色 | 在 Task 中的作用 |
| --- | --- |
| 需求方 | 解释业务诉求，决定优先取舍 |
| 验收方 | 决定结果能否被接受 |
| 结果接收方 | 接收或使用交付物 |
| 外部支持方 | 提供数据、权限、技术或领域判断 |

同一人可以承担多个角色。外部支持方还应写明**需要其提供什么**、**哪些判断依赖其答复**。例如“张三确认渠道接口口径是否变化，此确认影响根因判断”，比单记“技术支持：张三”更能指导 Agent。每次提问与答复记录来源消息，供下一次接手时核对。

## 3. 任务身份与拆分

建议围绕**业务对象或同一次问题、结果承诺、范围**判断同一性。来源、标题、群、thread、Agent 会话和工作阶段只是匹配线索。

router 从少量候选中核对业务对象、交付期次、步骤、已有承诺和引用材料。对每处有关的原文分别挂到相应任务，保留来源与理由；遇到新事项或归属不明的部分，挂项目根交由 owner 判断。比如“十月源表已到，另请更正九月验收口径”可同时挂两条任务。十月任务得到收件证据，九月任务的 owner 再核对这句话是否改变验收约定。仅挂材料也应能通过查询看到；是否需要唤醒、由谁对外答复另行决定。

树表达项目内的交付分解。每个非根任务有一个父节点，父子关系无环。task_owner 在能写出独立的交付结果和停止条件，并且值得单独委托、等待、并行或重开时创建子任务。月度交付的标准步骤可先保留为清单，有独立责任边界时才为该期建节点。跨任务共用的飞书证据用关联保存；父 owner 根据父任务的验收条件判断整体交付。

## 4. 不完整 Task 与关键缺口

创建 Task 不必要求所有信息已明确，但不能把空值统一解释为未知。对目标、范围、验收、反馈等关键约定，至少区分：

| 状态 | 含义 |
| --- | --- |
| 已明确 | 有可确认的约定，并保留其依据 |
| 暂定推断 | Agent 根据现有信息推测，尚未经有权方确认 |
| 待澄清 | 当前无法确定，需要指定的人回答 |
| 存在冲突 | 不同说法无法同时成立，需要裁决 |

用户明确表达的要求与 Agent 从代码或上下文推断的事实，不应具有相同的约束力。owner 更新约定时应引用提出者原文或决定依据。

每个会影响承诺边界的缺口，至少记录：

| 内容 | 示例 |
| --- | --- |
| 未知是什么 | 是否包含历史数据修复 |
| 为什么重要 | 会改变目标、验收和执行范围 |
| 谁能澄清 | 需求方或有决定权的负责人 |
| 澄清前能做什么 | 核查差异并整理影响范围 |
| 澄清前不能承诺什么 | 不能承诺完成历史回填 |

task_owner 根据已有证据写明缺口及澄清前允许的行动。若需要独立跟进，可建澄清子任务，委托 worker 拉取资料、向有决定权的人提问、记录回复。A 推荐改问 B 时，worker 在同一子任务中记录转介并跟进。能以证据说明问题不适用，也是一种有依据的结论。久未答复时记录未决原因，按约定提醒或交回。worker 遇到原契约无法成立时提出异议，owner 或接管的人决定是否改约。

## 5. 验收、再次唤醒与接管

已验收的任务进入稳定态，仍参与后续检索。新证据落在原承诺内时，可以唤醒 owner 再判断；产生另一份可独立验收的结果时，owner 可以新建关联的子任务。每次验收保留当时的契约版本、判断和证据。

任务进展、控制权、单次运行状态分别记录。人工接管使旧运行失去继续写入或外发的资格。接管期间照常接收和归档新证据，由人决定如何修订方向以及何时恢复自动处理。当前服务中 `done`、`cancelled` 的终态限制仍按[现行任务模型](../app/services/tasks/models.py)执行。
