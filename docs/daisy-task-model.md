# Daisy Task 身份与边界模型（讨论稿）

> 目标：先定义业务场景中一个 Task 代表什么，以及 Agent 拿到 Task 后如何判断自己应做什么、做到哪一步。本文暂不考虑旧模型兼容，也不设计执行过程、Event 层或材料索引层。

## 1. 核心定义

**Task 是针对一个有明确范围的业务问题，向特定对象承担的一份结果承诺。**

拿到 Task 后，Agent 应能回答：

1. 需要让什么事情发生变化？
2. 对哪些业务对象、时间、环境和人群负责？哪些不在范围内？
3. 什么结果算完成？哪些判断需要人来做？
4. 最终交付什么、交给谁、通过哪里反馈？
5. 哪些关键信息仍未知，澄清前能做什么、不能承诺什么？

来源可以有多个，但一个 Task 应当对应**一份连贯、可以判断是否完成的结果承诺**。标题、群聊、会话和 Agent 运行都不能单独定义 Task 的身份。

## 2. 模型的六个维度

| 维度 | 要回答的问题 | 建议记录的内容 |
| --- | --- | --- |
| 创建缘由（Origin） | 为什么产生这项任务？ | 触发来源、最初的业务问题、与父任务的关系；来源可以是飞书消息、工单、其他 Task 等，也可以逐步汇集多个线索 |
| 目标（Objective） | 希望得到什么业务结果？ | 预期变化或结论、结果作用的业务对象 |
| 范围（Scope） | 这份承诺管到哪里？ | 纳入项、排除项、适用时间、环境、人群、必要约束 |
| 验收（Acceptance） | 怎样证明结果已达成？ | 可检查的结果条件、交付要求、接受方式和决定权 |
| 反馈约定（Feedback） | 结果交给谁、交到哪里？ | 接收方、反馈位置、反馈内容与形式 |
| 相关方（Parties） | 谁能提供信息、支持或决定？ | 需求方、验收方、结果接收方、外部支持方及各自职责 |

这些是语义维度，并非立即落地的数据库字段清单。Task 描述的是当前承担的责任；实际沟通、运行和进度变化留给后续 Event 层。

### 目标与验收的区别

**目标**描述业务上希望成立的事实；**验收**描述如何确认它成立。验收可以再拆为：

1. **结果条件**：必须成立的事实或达到的标准。
2. **交付要求**：必须留下什么可检查的产物或依据。
3. **接受方式**：Agent 可以依条件自行判定，还是必须由指定的人确认。

例如，业务方说“昨天的渠道收入数据不对，帮忙看一下”，若约定本次只负责调查：

| 项目 | 可能的定义 |
| --- | --- |
| 目标 | 查明指定日期渠道收入差异的原因，为是否修复提供依据 |
| 范围 | 指定报表、日期、渠道及相应计算链路；不负责修复数据或重跑生产任务 |
| 交付物 | 原因分析和处理建议 |
| 验收条件 | 说明差异口径与数值；定位原因并给出依据；说明影响范围；提出处理建议或明确尚不能判断的部分 |

“写出报告”只证明交付物存在；“问题已查明”如果没有证据标准，也不足以让 Agent 判断完成。探索性任务还应约定**调查到什么程度可以结束**：例如完成指定核查后仍未定位时，交付已排除项、剩余假设和下一步所需材料，并由需求方决定是否接受。临时缺材料通常意味着受阻，不能由 Agent 自行把目标降格为已完成。

### 来源、反馈与决定权

应分别表达：

- **来源**：承诺为何产生、最初依据是什么。
- **结果接收方**：谁需要取得或使用结果。
- **反馈位置**：结果发布到哪个飞书 thread、工单或其他位置。
- **验收方**：谁有权认定结果符合要求。

飞书 thread 是位置，不是一个人或一项决定权。可以默认反馈到触发任务的 thread，但这个默认值应允许调整，也不参与任务身份判定。子任务常向父任务交付结果，子任务完成也不自动意味着父任务完成。

### 相关方的职责

| 角色 | 在 Task 中的作用 |
| --- | --- |
| 需求方 | 解释业务诉求，决定优先取舍 |
| 验收方 | 决定结果能否被接受 |
| 结果接收方 | 接收或使用交付物 |
| 外部支持方 | 提供数据、权限、技术或领域判断 |

同一人可以承担多个角色。外部支持方还应写明**需要其提供什么**、**哪些判断依赖其答复**。例如“张三确认渠道接口口径是否变化，此确认影响根因判断”，比单记“技术支持：张三”更能指导 Agent。联系的时间和答复内容以后由 Event 层记录。

## 3. 任务身份与拆分

建议围绕**业务对象或同一次问题、结果承诺、范围**判断同一性。来源、标题、群、thread、Agent 会话和工作阶段只是匹配线索。

Dispatcher 可依次判断：

1. 是否指向同一业务对象或同一次问题，例如同一工单、事故、批次数据？
2. 是否追求同一个预期结果，例如“查明原因”和“完成修复”是否已被约定为同一份承诺？
3. 范围是否一致或相容，例如日期、对象、环境和人群有无变化？
4. 新信息是在补充原任务，还是增加或改变了必须验收的责任？

同一异常在别的群补一张截图、次日追问进展，通常仍属原 Task。原话题要求修复另一个月份的数据，则可能产生新 Task 或范围变更。研究、规划、执行阶段的切换本身不产生新 Task；若原承诺就是修复异常，调查和规划可以只是履行它的步骤。

一个实用拆分检验是：**两部分能否独立验收、独立放弃，而不使另一部分的完成失去意义？** 如果可以，值得考虑拆为两个 Task；最终仍要看业务上是否愿意分别承担这两份结果。

Dispatcher 的语义判断建议能区分：

- 同一任务的材料补充或澄清；
- 对现有任务提出目标或范围变更；
- 新任务，且与旧任务存在关联；
- 暂时无法判断归属。

即使实现时映射到较少的接口，也应保留这些区别，避免把“顺便把历史数据都修了”作为普通跟进，悄悄扩大原任务的责任。

## 4. 不完整 Task 与关键缺口

创建 Task 不必要求所有信息已明确，但不能把空值统一解释为未知。对目标、范围、验收、反馈等关键约定，至少区分：

| 状态 | 含义 |
| --- | --- |
| 已明确 | 有可确认的约定，并保留其依据 |
| 暂定推断 | Agent 根据现有信息推测，尚未经有权方确认 |
| 待澄清 | 当前无法确定，需要指定的人回答 |
| 存在冲突 | 不同说法无法同时成立，需要裁决 |

用户明确表达的要求与 Agent 从代码或上下文推断的事实，不应具有相同的约束力。此处只需给未来的材料依据保留关联位置，暂不设计索引实现。

每个会影响承诺边界的缺口，至少记录：

| 内容 | 示例 |
| --- | --- |
| 未知是什么 | 是否包含历史数据修复 |
| 为什么重要 | 会改变目标、验收和执行范围 |
| 谁能澄清 | 需求方或有决定权的负责人 |
| 澄清前能做什么 | 核查差异并整理影响范围 |
| 澄清前不能承诺什么 | 不能承诺完成历史回填 |

Researcher 首先应把初始诉求整理成**可履行、可验收的任务约定**，找出缺口，并指出哪些可通过调查补齐，哪些必须由人决策。技术调查可以提出“如何证明修复有效”；可接受误差、是否补历史数据等业务取舍应保留给相应的决定者。

## 5. 对 Daisy 的落地优先级

优先明确 **Objective、Scope、Acceptance、Feedback 与关键缺口**。标题可作为摘要，`readonly / operational` 可作为辅助分类；Dispatcher 判断同一性、Researcher 判断下一步，主要依靠结果承诺及其边界。

本稿停留在 Task 的业务语义层。字段结构、状态机、版本变更、Event 与材料索引，以及具体执行权限，留待后续设计。
